# AI usage and engineering traceability

This concise log records the material AI-assisted tasks in this repository. The engineer defined the requests, reviewed the outputs on the local machine, and owns the final design, validation, and submission decisions.

## Engineer-led iterative workflow

The work was completed as an iterative collaboration, not as an unreviewed AI code drop:

1. The engineer provided the task goal, constraints, and relevant source/document references.
2. AI proposed code, tests, configuration, or documentation for the requested scope.
3. The engineer reviewed the result, tested APIs locally where applicable, and asked for corrections or additions when the output did not fully match the intended design.
4. AI implemented the requested revision and reported the validation result.
5. The engineer decided whether the revised result belonged in the repository after review; the engineer retains ownership of every included change.

Examples of engineer-directed revisions in this work include changing the documentation scenario mapping, requesting H2 direct-datastore tampering coverage, correcting stale test-count documentation, refining JWT/Postman guidance, and expanding deferred-work and AI-traceability details. These revisions demonstrate that AI suggestions were reviewed and adjusted through engineer feedback rather than adopted automatically.

## Not adopted or intentionally deferred

- **No unsupported compliance-reporting code was added for Scenario C.** The product statement lacks jurisdiction, required fields, recipient workflow, and retention/legal-hold policy. A design and explicit scope boundary were documented instead of inventing compliance behavior.
- **No KMS/HSM-backed export signing key was added.** The prototype generates an Ed25519 signing key in the service process. Durable key storage, rotation, historical public-key retention, and trusted fingerprint distribution require production infrastructure and security ownership.
- **No multi-instance chain coordinator was added.** The current append synchronization protects one JVM. Database serialization, optimistic retries, or a dedicated sequencer should be chosen only after deployment topology and throughput requirements are known.
- **No fine-grained authorization model was added.** JWT authentication protects the API, but separate privileges for audit read, redaction, retention, export, compliance reporting, and operations need an identity-provider and authorization-policy decision.
- **No JWT revocation, refresh-token, or key-rotation service was added.** The prototype uses short-lived HS256 access tokens. Session lifecycle, emergency revocation, issuer/audience rules, and secret rotation need enterprise identity/security requirements.
- **No legal-hold or physical-purge workflow was added.** Soft archival preserves chain evidence, but legal holds, backup expiry, encrypted-field key destruction, and approved deletion policy require legal/compliance direction.
- **No Flyway/Liquibase migration workflow was added.** The shared schema initialization is appropriate for local development and tests; controlled PostgreSQL migrations belong in the deployment/CI process.
- **No regulator-specific CSV/PDF report generator was added.** The existing signed JSON export is the integrity foundation. The regulator, report layout, delivery channel, and evidence rules are intentionally unresolved in Scenario C.
- **No AI output is included automatically.** Changes are made only after an engineer request and are subject to local review and validation.

## Use boundaries

AI was used as an engineering assistant for analysis, implementation suggestions, debugging, tests, and documentation. It was not treated as an autonomous decision maker. The engineer owns the design choices, reviews generated changes, validates behavior locally, and decides what is included in the final repository.
